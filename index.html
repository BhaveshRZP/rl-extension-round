Why not RWMutex, sync.Map or a lock per user? likely follow-up

RWMutex: every Allow writes, so you'd always take the write lock. You pay for reader tracking and get nothing back.

sync.Map: it's built for keys written once and read many times, or for goroutines working on separate keys. We write on every call, and we'd still need the read, check and append to happen together.

A lock per user: you still need a map lock for get-or-create. You'd also have to keep a lock order, and eviction in stage 4 brings a reactivation race. Shards get most of the gain with one lock per call (see 3b).

One lock for every user is a bottleneck. Can you do better without breaking correctness?

Invariant: a user always hashes to the same shard. A shard's lock guards its map and every slice in it, so each call takes exactly one lock.

Why a list, and what it assumes likely follow-up

The list gives O(1) moves and O(1) evictions. It's exact with one shared timeline, where each call's timestamp is the newest so far. If users' timestamps arrive out of order with each other, the list can stop at a fresher user, so some idle users are evicted late.

The same lag causes a worse problem. A user whose own timestamps trail the global "now" looks idle while its timestamps still count, so it can be evicted and then over-admitted. With 3 per 10 s and TTL 10: u1 at 1, 2, 3, then u2 at 100, then u1 at 4 is allowed. No list or heap fixes that. It needs one clock (server-stamped time), or a TTL of at least the widest window plus the largest lag.

A min-heap keyed by lastSeen (container/heap with heap.Fix) removes only the "late" case, at O(log n) per call. A timing wheel buckets users by expiry second, which is cheap when the TTL is small and fixed.

Tell the caller when to retry Remaining and Retry-After

Add Decide, which returns Decision{Allowed, Remaining, RetryAfter}, and keep Allow as a one-line wrapper so no caller or test breaks.

For each full limit, the blocking entry ts[k] leaves that limit's window at ts[k] + W. The request can pass once the last of them has left, so RetryAfter = the largest ts[k] + W − t over the full limits. Rejects record nothing, so nothing can push that time later. A test checks this against the brute-force oracle on random traces: at t + RetryAfter the request passes, and one second earlier it doesn't.

Remaining is the smallest max − count over the limits after this call. The code finds each count with sort.SearchInts on the sorted log.

A global limit on top of per-user check both, record both

A request passes only if its user is under the per-user limit and all users together are under the global one. Check both, then record in both. A reject records nothing, but still saves both trims, as in stage 2, so a burst of rejects doesn't rescan expired entries.

One shared count needs one lock, and shards can't split it. If they push on contention, one idea is to give each shard a slice of the global budget and rebalance now and then. That trades exactness for less contention. It's only a talking point here; it isn't in the tested code.

Put it in front of an HTTP API 429 and Retry-After

The middleware asks Decide and, on a reject, responds 429 Too Many Requests with a Retry-After header in seconds. The clock is passed in as a function, so a test can fake it.

It clamps t up to the newest entry because now() is read before the lock. The Decide in "Tell the caller when to retry" has no lock, like stage 2: give it the stage-3 mutex or the 3b shards first.

Late timestamps: three policies what stage 3's clamp gives up

Under concurrency, a goroutine holding t=1 can reach the lock after one holding t=2. The k-th-newest check from stage 2 needs the log sorted, so pick a policy and say it out loud:

PolicyWhat it doesWrong by real timestamps?
Clamp (stages 3–4 here)Treat t as the newest recorded timeBoth ways. With 2 per 10 s: calls at 1, 2 and 12, then a late 10, all get in, because 1 and 2 were trimmed when 12 arrived. Calls at 20, then a late 5, then 29 give T T F, where the rule says T T T, because the late call is recorded at 20 and stays in the window longer.
Reject lateRefuse any t below the newest recorded timeNever lets too many in. It can refuse an allowable call, depending on which goroutine got the lock first.
Exact insertInsert t in sorted position if every window containing it stays within maxExact for calls up to W−1 behind the newest. Older ones are refused, because the history they need is gone. It stores up to 2×max per user.

In 3,000 random late traces, the clamp over-admitted by real timestamps in 1,326 of them, and never on its recorded log. Reject-late and exact insert never over-admitted.

The doc's stage-3 rules say "no request may bypass limits due to race conditions". Read by real timestamps, only reject-late and exact insert meet that.

Say: "I clamp, so the log stays sorted and my recorded log always obeys the limit. Lock order still changes answers: at 1 per second, if t=2 locks first, the late 1 is counted at 2 and rejected, and by real timestamps the clamp can also let in calls that should be refused.
